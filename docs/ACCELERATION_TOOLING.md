# Acceleration tooling and quality gates

## Purpose

This repository is a static Pokémon team generator with ROM-derived data. The goal of this tooling is to make each batch auditable and repeatable, detect regressions early, and prevent unverified mappings from silently becoming runtime facts.

## Automated checks

The `Quality checks` GitHub Actions workflow runs on pull requests targeting `main` and manual dispatch. It now separates static/data/strategy tests from Playwright browser regression tests into independent jobs so they can run concurrently. Each job installs from the same lockfile; only the browser job installs Chromium. The GitHub Pages workflow still runs the complete `npm test` suite before deployment on pushes to `main`, preserving a single full pre-deploy gate:

- `test:static`: generator and data invariants.
- `test:rom-audits`: ROM audit schema and integrity assertions.
- `test:browser`: browser interaction regression tests.
- `test:tooling`: verifies required audit inputs, npm test wiring, CI triggers, and the Pages deployment gate.

The repository commits `package-lock.json` (lockfile v3) generated by npm in the Node.js 22 CI environment. Both workflows use `npm ci` and setup-node's lockfile-aware npm cache, so CI installs follow the pinned dependency tree. Dependabot checks npm and GitHub Actions updates weekly; its pull requests are subject to the same quality gates. After changing dependencies, regenerate and commit the lockfile with npm rather than editing it by hand.

A red check means the batch is not validated. Do not label a batch complete or update progress as verified until the workflow passes.

## ROM data rules

- Keep raw IDs, source ROM identity, hashes, and evidence attached to derived records.
- Treat name mappings and gameplay interpretations as candidates until independently verified.
- Never transfer a type/effect interpretation from one ROM profile to another without evidence.
- Keep structural binary comparison separate from semantic certification.
- Unknown entries stay explicitly unknown; never infer names from archive position alone.

## Efficient batch workflow

1. Identify a bounded batch with clear input files and expected output.
2. Run the narrow audit/test for that batch while unrelated, independent audits are prepared in parallel.
3. Run the full `npm test` suite before accepting the batch.
4. Record the source commit, audit inputs, counts, unresolved items, test result, and next action.
5. Reuse existing parsed exports and audit artifacts rather than repeating extraction.
6. Prioritize blockers that unlock multiple downstream tasks; do not parallelize tasks that depend on an unfinished mapping.

## Progress accounting

Progress is evidence-based, not time-based. Track separate workstreams (ROM extraction, mapping verification, generator integration, regression coverage). Each task has a defined acceptance condition and weight. A task only counts as complete when its evidence exists and its acceptance check passes. Report:
- last verified commit SHA and timestamp;
- completed / total weighted tasks per workstream;
- tests run and pass/fail status;
- blockers and unverified assumptions.

Do not average percentages from different workstreams unless a documented weighting model defines how they combine. Do not claim background progress between sessions.

## Deployment

GitHub Pages deployment is configured separately in `.github/workflows/pages.yml`. This quality workflow is a required practical preflight, but repository branch protection is an account-level setting and is not enabled by this file. Configure a required status check in GitHub branch protection if direct pushes must also be prevented.

### Direct binary audits (local only)

The original ROM binaries are intentionally not committed to this repository. With the exact CPUF and CPUE `.nds` files available locally, run:

```sh
npm run audit:rom:types -- "/path/to/CPUF.nds" "/path/to/CPUE.nds"
npm run audit:rom:evolutions -- "/path/to/CPUF.nds" "/path/to/CPUE.nds"
npm run audit:rom:names -- "/path/to/CPUF.nds" "/path/to/CPUE.nds"
```

All three commands verify the game code and exact SHA-256 before parsing NitroFS/NARC records. They fail closed if a different ROM revision is supplied. Their output is a raw-byte audit, not a claim that custom Project PM mechanics or every internal ID's display name has been semantically decoded. The CI suite validates the checked-in audit summaries and guardrails; it does not need or redistribute the ROM binaries.


## Project PM Fairy-move semantic hypotheses

`data/project_pm_fairy_move_semantics_audit.json` records the eight CPUE move IDs whose raw type byte is 9. The decoded move-name bank resolves their French display names, and the pinned canonical effect table is used only to create explicit hypotheses from matching effect IDs and parameters. Those symbols are not proof of CPUE battle-handler behavior. The audit and `scripts/validate-rom-audits.mjs` must keep every hypothesis marked unverified for Project PM runtime and Gen IV mechanics until direct handler evidence or controlled in-game tests are available. Do not activate these candidate effects in the generator.


## Cross-ROM level-up move usage audit

`data/project_pm_levelup_move_usage_audit.json` compares level-up references for the eight CPUE Fairy-type move entries and the four additional CPUE moves at IDs 468–471. It reports counts and species/level references at the same numeric ID only. IDs with changed names and CPUE-only IDs are explicitly marked as unsafe for semantic comparison; usage-count differences must never be read as proof that CPUF and CPUE moves have the same identity. The audit validates all 493 standard-species learnset rows in each ROM and records zero invalid move references in the extracted tables.
